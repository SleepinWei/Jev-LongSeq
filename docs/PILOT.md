# BrowserGym 与真实模型：两项长任务 pilot

日期：2026-09-27。本轮严格只启动 **2 个真实模型任务**，没有运行矩阵、第三次尝试或隐藏的成功重跑。

结论：执行链路已接通，**两项均失败**。这些是 BrowserGym 中注册的自建目录任务，不是官方 WebArena / WebChoreArena 成绩。规则策略的历史成功率没有混入本轮结果。

## 环境与模型

- Python 3.13.13；BrowserGym core / WebArena adapter 0.13.3；libwebarena 0.0.4；Playwright 1.63.0；Chromium 153.0.8010.12。
- Jev 请求别名 `jev-latest`，服务实际返回版本 **`jev-1.13.0`**。
- 生成式事件规划器使用现有配置的 **`deepseek-flash`**；本轮没有生成式局部策略或规则策略替代 Jev。
- 任务为逐页查看所有目录记录，仅保存 `Rating >= 4 && Price <= 60` 的记录，逐条读回；本轮没有额外启用弹窗/提示注入故障。
- 每次仅执行一个状态改变动作，候选上限 32，规划上限 4 次，任务总限时 600 秒。两个任务的动作预算分别为 140 / 160。
- 模型凭据从显式指定的既有 `.env` 文件读入；未复制到项目或运行产物。

### 第一个任务：连接中断

真实规划器生成了子任务 DAG；Jev 读取并保存了第一条记录，读回通过，随后回到列表。后续 Jev 请求出现连接错误并耗尽当前请求的有界重试，任务中止。

HTTP 尝试全部进入账本：4 次 Jev 成功、4 次 Jev 连接失败、1 次规划成功。已返回 usage 的调用合计 **31,918 输入 tokens、19,225 输出 tokens**；失败请求 usage 不可知。

### 第二个任务：往返循环与规划格式错误

第二次试跑前修改了 HTTP 客户端，使连接池在整次运行内复用。该次 67 个 Jev 请求全部返回 200；一次规划器连接失败后重试成功。两次代码版本不同，因此不能将其解释为严格配对性能实验。

Jev 保存第一条记录后反复进入第二条记录详情再返回列表，没有调用抽取动作将页面事实保存到验证记忆。单步页面一直变化，原来的“连续相同状态”检测未识别这种两页面循环；子任务动作预算触发了重规划。

第三次规划返回的顶层 JSON 多出 `"type": "json_object"`，与严格 Plan schema 不符。Pydantic 拒绝该输出，运行停止；没有将格式不合法的规划作为可执行任务。

已返回 usage 的调用合计 **598,070 输入 tokens、63,786 输出 tokens**。其中规划器有 1 次连接失败，usage 不可知。这里的输出 token 按服务端 usage 原样计入，可能包含服务端计量的推理 tokens。

## 本轮修复与测试

- 模型 HTTP 连接池按运行复用，连接错误有界重试，失败调用保留在账本；调用方提供的 client 不被擅自关闭。
- 新增往返循环检测：页面重复出现但事实和已完成子任务没有进展时升级，覆盖 A→B→A→B 的情况。
- 已完成子任务的 `final_answer` 绑定继续可用于向公共 benchmark 提交终答，避免契约推进后丢失答案。
- 显式 dotenv 加载不执行 shell；BrowserGym 动作参数用安全字面量序列化；判分与模型观察分离。

**往返检测修复在第二次任务完成后加入，仅做自动测试，没有再启动第三个真实模型任务；不能声称它已经让该长任务成功。** 当前仍需改善 Jev 的抽取/进度策略以及规划器的严格结构输出。

最终回归 **42 项通过**，测试输出见 [test-report-benchmark.txt](test-report-benchmark.txt)，Ruff 检查与格式检查通过。两次短环境生命周期的集成测试与模型 benchmark 是分开计数的。
