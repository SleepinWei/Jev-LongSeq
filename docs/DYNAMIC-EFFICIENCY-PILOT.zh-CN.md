# 大小脑反馈循环：两次真实模型效率试跑

日期：2026-09-27。真实模型：Jev `jev-1.13.0`，LLM `deepseek-flash`。共两次任务启动，没有追加重跑。

## 条件

同一个 12 条记录自建目录任务，Playwright 后端，动态模式；只向 agent 提供自然语言目标，没有控件规则、实体清单、字段白名单或成功谓词。候选上限 64、动作上限 65、LLM 调用上限 48、墙钟上限 360 秒，不启用 live preview。独立环境判分只在控制器停止后执行。

两次使用完全相同的代码与 fixture：

- code hash：`9755f5d855c582f675ffa9f9a9e38795dbbfb63443f3612fe41068c5ebd26296`
- fixture hash：`baa74da857c6c250032fcad9953c8c5d7a517358fb443d67d85bcc9a7fc3cff3`
- 唯一实验参数差异：`brain_interval=12` 与 `brain_interval=1`。

稀疏运行先执行；其开始阶段与离线回归测试存在短暂重叠，不能把本次墙钟结果当作严格隔离的性能测量。模型连接故障进一步破坏了完整任务对照。

稀疏运行得到 3 次合法大脑指导；另一次成功 HTTP 返回了多余的 `next_candidates` 字段，严格校验拒绝后纠正成功。它完成了全部记录的页面操作，但最终又向前翻了两页，随后在不确定结果的 LLM 调用中连接失败。环境的保存集合和访问覆盖均正确，不代表 agent 已正确判断完成。因此 `grade.strict_success=true` 与 `result.strict_success=false` 同时保留，不能只选环境分数报告为端到端成功。

每步大脑对照在处理第一条记录时即因 LLM 连接失败停止，低总 tokens 和短墙钟主要来自提前失败，不能算效率优势。

## 可以确认什么

- 没有任务专用规则的动态候选与通用可见证据链路确实运行；稀疏模式中 Jev 能在 LLM 调用之间连续推进多个记录。
- 结果判断与动作选择已在同一个 Jev 请求中完成，没有每步额外串行请求结果模型。
- 稀疏运行的 31 次实际点击只产生 3 次合法阶段指导，但仍存在摘要覆盖/收尾判断问题、格式纠正开销和连接故障。
- **不能计算有效加速比、成本下降比例或成功率提升**：两次都没有正常结束，而且处理工作量不同。每动作 tokens/耗时仅为报告中的描述指标，不能替代同质量的完整任务对照。

## 试跑后的离线修正

为避免下一阶段指导还未生效就执行旧动作，增加了“Jev 请求大脑后丢弃原先候选选择、重新决策”的路径及测试。小脑上下文补充当前阶段已执行动作的简短列表，以减少只靠最后几个页面造成的进度遗忘；大脑提示独立于 Jev 的候选操作说明，并要求减少重复输出。这些改动经过离线验证，**没有再调用真实模型试跑**；上表只描述前述 hash 的两次运行。

离线的同一表单调度对照保持 4 次浏览器动作都成功，LLM 逻辑调用从每步模式的 8 次降为稀疏模式的 4 次（其中 2 次都是输入助手）。这是控制流计数测试，不是真实模型 token 或延迟测量。
