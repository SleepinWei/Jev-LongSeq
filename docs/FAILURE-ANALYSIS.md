# 两次真实模型试跑失败分析

分析日期：2026-09-27。依据已有两次运行的轨迹、记忆、回执、报告和实现代码；本次仅做离线回放，没有新增浏览器任务或模型调用。

后续已按此分析完成一轮实现修复与本地回归，见 [修复验证记录](RECOVERY-VERIFICATION.zh-CN.md)。下文保留对修复前运行的分析，代码行号对应分析当时的版本。

## 结论

第一项由连接错误直接中止。第二项首先在第 2 条记录发生持续往返，之后由规划输出不符合 schema 中止。第二项的主要进度问题是局部策略未选择抽取，而接入实现没有可靠地衔接“页面观察 → 持久事实 → 实体进度 → 下一动作”。只修复最终 JSON 报错，不能解决此前已经存在的循环。

这两个样例尚不足以判断 Jev 的整体长任务能力：第二项只访问了 2/32 条记录，就已暴露基础执行与记忆协作问题。两项都是 BrowserGym 自建任务，不是官方 WebArena / WebChoreArena 成绩。

## 1. 第一项：连接错误，底层原因无法由现有日志确定

轨迹目录：`runs/pilot-jev-gym-01/catalog-24-0/`。

- 执行 5 个动作，完成第一条记录的保存和读回，返回列表后中止。
- Jev 共 8 次 HTTP 尝试，4 次成功、4 次连接失败；有界重试耗尽后报 `ConnectError`。
- 日志没有保留足以进一步区分代理、TLS、连接复用或服务端断连的底层异常信息。因此不能把它确定归因于服务宕机或密钥无效。
- 当时每次决策创建、关闭 HTTP 客户端。第二项前改成运行内连接池复用；第二项 Jev 67/67 次请求成功，但这不是受控对照，不能证明连接池改动彻底解决了网络问题。第二项规划器仍有一次 `ConnectError(EndOfStream())`，重试后成功。

## 2. 第二项：先失去业务进度，再遇到格式异常

轨迹目录：`runs/pilot-jev-gym-02/catalog-32-0/`。

### 2.1 正确动作存在，但没有被选中

第一次进入 item-002 时，页面明确显示：

```text
Entity: item-002
Rating: 1
Price: 33
Saved: no
```

它不符合保存条件，正确流程是记录这些可见事实，再返回并处理后续记录。轨迹第 19 行的候选包含 `a2=extract_visible` 和 `a5=Back`，Jev 选择了 `a5`。

全程统计：

| 事实 | 数量 |
|---|---:|
| 进入 item-002 后的决策 | 31 |
| 上述决策中提供抽取候选 | 31 |
| 上述决策选择 Back | 31 |
| Jev 主动选择抽取 | 0 |
| 控制器自动抽取 | 1 |
| 总动作 | 68 |

因此，这是已提供候选中的选择问题，不是缺少抽取候选。所有已执行动作回执成功、grounding rejection 为 0，也没有证据表明浏览器点击失效。

### 2.2 自动读回掩盖了第一条记录的抽取缺失

`controller.py:163` 只有在执行 `extract_visible` 成功后才写入结构化事实；`controller.py:220` 对待确认写入会强制执行读回抽取。

item-001 被保存，因此自动读回顺带记录了 Rating、Price、Saved。item-002 无需保存，没有触发自动读回，Jev 又跳过主动抽取，于是其结构化事实始终为空。第一条记录的成功并不说明策略掌握了抽取流程。

离线回放使用日志里已经出现的 item-002 页面，调用现有解析与校验代码：

- 仅观察页面后，`processed(item-002) = false`。
- 显式抽取 Rating、Price、Saved 后，`processed(item-002) = true`。

这证明该页面信息足以通过单条记录校验；不等于证明加上抽取后整项任务必然成功。结果保存于 [failure-analysis-replay.json](failure-analysis-replay.json)。

### 2.3 记忆表示使错误难以自我纠正

`memory.py:38` 的页面摘要按 URL 存储，同 URL 后一次观察覆盖前一次。此任务列表和详情均为 `about:blank`，返回列表立即覆盖详情摘要。离线回放确认，详情 → 列表之后仅保留一条页面摘要，其中已无 item-002 详情。同 URL 的真实单页应用也可能遇到这种覆盖。

`controller.py:166` 写入策略可见的近期事件只有 operation 和 receipt，没有动作描述、实体与前后页面状态。反复点击在模型上下文里主要表现为通用 click 回执。完整轨迹中的信息比模型实际收到的近期记忆丰富，不能用“日志里有”推断“模型上下文里也有”。

所以可以确认：item-002 的验证事实缺失，详情摘要被覆盖，近期动作语义不足。它们是循环的实现层促成因素；日志不能揭示模型内部为何每次偏好 Back。

### 2.4 子任务与恢复反馈没有定位缺失证据

初始计划（轨迹第 2 行）把 5 条记录放入一个子任务，动作上限 32；第一次重规划（第 100 行）仍按 5 条记录分组，上限改为 36，目标虽明确写了 extract，仍未打破循环。

`controller.py:76` 的重规划输入包括任务、当前观察、记忆和原因字符串，但没有显式提供旧契约、未满足谓词清单、循环实体与动作摘要。规划器收到的是 `subtask_budget`，而不是可操作的“item-002 被查看 15 次但 Rating/Price/Saved 尚未落入事实记忆”等诊断。

运行当时的停滞检测仅比较相邻状态；列表与详情交替变化会重置计数，所以只能等 32/36 动作的子任务预算耗尽。第二项之后已加入无事实进展时的重复页面检测，并通过单元测试；尚未做真实模型复验。这个修复能提前识别循环，不能单独保证恢复成功。

## 3. 最终异常：JSON 合法不等于 Plan 合法

第三次规划被 Pydantic 拒绝：

```text
ValidationError: 1 validation error for Plan
type
  Extra inputs are not permitted
  input_value='json_object'
```

`models.py:188` 把 Plan schema 放在提示词中，但请求只指定 `response_format={"type":"json_object"}`；这约束 JSON 语法，不能保证输出满足 Plan schema。随后直接调用 `Plan.model_validate_json`，没有针对校验错误的有界纠正流程；`controller.py:177` 捕获异常后结束整个任务。

可以确认响应包含不允许的顶层 `type` 字段。原始无效响应没有保存，无法完整复核响应形状，也无法确认该字段为何出现。“模型将 response_format 元数据混入正文”只是可能解释。

严格拒绝非法计划是正确行为。应改善结构生成、错误恢复和诊断留存，而不是关闭校验或静默丢弃任意字段。

## 4. 为什么自动测试通过，真实策略仍失败

42 项自动测试通过，不等于真实模型任务通过。`fixture.py:189` 的规则策略把关键步骤写死：若页面字段尚未进入记忆，优先选择 EXTRACT；之后才判断保存或返回。因此规则流程天然避开了此次失效路径。现有测试可以验证协议和控制器机制，但不能替代真实策略对这些机制的使用验证。

此外，第二项规划器 HTTP 耗时合计约 187.6 秒，占端到端约 262.9 秒的 71%；Jev 的 67 次请求累计输入 542,018 tokens，平均约 8,090 tokens/次。大计划、重复上下文和无效循环带来显著开销，但没有证据支持“超过上下文容量导致失败”的判断。

## 5. 建议修复顺序

1. **先闭合证据与进度链路。** 对已完整显示、任务声明需要的字段，采用带来源的确定性抽取，或增加离开详情前的证据检查。明确区分“已查看”“已记录且不符合条件”“已写入并读回”。这类机制应统一用于比较基线，并如实计入抽取动作或处理成本。
2. **改善策略可见记忆。** 页面摘要使用 URL 加实体/视图标识区分；近期事件包含实体、动作描述、执行结果和状态变化，给出下一条未验证记录。保留有界记忆，避免无差别累积上下文。
3. **让重规划针对具体失败。** 传入未满足谓词、重复动作和缺失字段；按实体或其他可验证边界推进，减少反馈延迟。动作预算应校准，不能只把提示词里的“通常 3–8 步”当作已实现的约束。
4. **补规划输出恢复。** 在供应商支持时使用严格 schema 输出；否则增加一次有预算限制的校验纠正请求，并保留脱敏后的无效响应与错误位置。仍需先校验后执行。
5. **最后优化调用成本与网络诊断。** 缩减重复 schema/谓词上下文；记录异常链与请求标识，在现有连接池、有界重试基础上调查偶发连接故障。

本次分析只新增此报告及离线回放结果，没有修改运行逻辑，没有追加真实模型 benchmark。后续优先验证“无需保存的记录也能记录证据并推进到下一条”，再考虑更长任务。
